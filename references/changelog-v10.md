## v10.8 变更（2026-09-13 · 两家复审 v10.7 后）

两家共 9 条：**已修 4、误报推翻 2、明确不做 3**。

### 一、P1：正常日报每天都天然 degraded（真实逻辑 bug）

`build_data_quality()` 里基本面用 **持仓总数** 当分母：

```
fund_ok = 6       （6 只 ETF 全部成功）
expected = 9      （持仓总数，含 3 个加密）
→ 6 < 9 → FUNDAMENTALS_DEGRADED → severity = degraded
```

而采集侧本来就只对 `ETF_TICKERS` 取基本面（`for sym in positions: if sym in ETF_TICKERS`）——
**加密结构上就没有基本面**。于是无论数据多正常，日报永远 degraded，`degraded` 这个信号等于作废。

更糟的是：**契约测试把这个错误固化成了不变量** ——
`for key in ("行情", "基本面", "ML"): if exp != n_pos: bad(...)`，
它要求基本面分母必须等于持仓数，等于替 bug 站岗。

修法：

- 分出 `fund_expected = len(positions ∩ ETF_TICKERS)`，用它替代 `expected`；
- 契约测试改成按资产类别分开：行情/ML 用持仓数，**基本面用 ETF ∩ 持仓**；
- 新增变异样本「基本面分母含加密」（9 个持仓、6 只 ETF、分母写 9）——
  实测报出 `基本面分母 9 != 适用标的数 6（ETF ∩ 持仓）—— 加密没有基本面，不能进分母`。

修后实测：`基本面 6/6`，`FUNDAMENTALS_DEGRADED` 消失；severity 仍是 degraded，
但只剩 `SOURCE_FAILED`（CoinMetrics 429）这个**真实**原因 —— 这才是 degraded 该有的样子。

### 二、P2：模型缺训练溯源 / 特征实现两份 / description 版本号

| 项 | 处理 |
|---|---|
| 模型无训练时间与数据范围 | 补 `train_start` / `train_end`；报告显示「模型训练信息：<日期>训练，数据范围 A ~ B，CV-RMSE x% ± y%（5 折，gap=horizon）」 |
| 训练/生产各一份特征实现 | 新增 `check_feature_parity`：同一 600 根合成序列上比生产原语（`calc_rsi`/`calc_ma`）与训练实现的末值。实测把生产侧 RSI 人为偏 5 会立刻报 `rsi14：生产侧 75.22360613 != 训练侧 70.22360613`。**用检查哨代替大重构** —— 真重构（让 backfill 复用 features 的实现）留作后续，代价与收益要另算 |
| `config.description` 版本漂移 | 直接去掉 description 里的版本号，并加 `check_config_description`：出现版本号即失败。理由：这个字段没有任何校验者，必然漂移；版本只写在 `config.version` |

### 四、明确不做（附理由）

- **ML 缺失特征改成数值阈值**（如「缺失 ≤2 正常 / 3~5 degraded / >5 不可用」）：
  本项目第一公理是**不自造阈值**。现在的规则是分类式的、有依据的：
  「加密专属特征对美股结构性缺失，不算；其余任何一个缺失即不可用」。
  引入人为数字会让这条规则失去可解释性。
- **`NEWS_TRANSLATION_MISSING` 失败码**：新闻翻译由 cron 里的 agent 步骤在流水线**之后**回写，
  流水线产物本来就不含译文 —— 加这个码会让**每一轮都误报 degraded**，
  正是本版刚修掉的那类 bug（信号恒亮 = 信号作废）。译文的降级已在报告里显式标注。

## 硬教训：数据质量的分母不能自指（2026-09-12 第二次踩到同类）

**症状**：9 个持仓里有 3 个（全部加密标的）**整个消失**，但 `data_quality` 报「行情 6/6」、
collect 退出码 0、报告照常生成 —— 读者完全看不出残缺。

**根因**：`build_data_quality(output, len(output.get("tech") or {}))` —— 分母取自**产出本身**。
标的采失败时 `tech` 变短，分母跟着变小，于是「丢了 3 个」被算成「6 个全成功」。

**修法**：分母用 `len(output["positions"])`（**应该**有多少持仓），且 `priced < expected`
时显式标 `fail(6/9)`，不再用「部分成功」的写法掩盖。

**同类事故已发生两次**（第一次是配置路径找不到 → 静默返回 `{}`）。
规律：**凡是「用产出反推健康度」的指标，分母必须来自独立的期望值，不能来自产出本身。**
新增任何 data_quality 指标时，先问一句：这个分母会不会因为东西丢了而一起变小？

### 附带发现：try 块内的赋值会静默吞掉整块逻辑

把 `output["config_version"] = str(cfg.get("version"))` 写进「1. Ghostfolio 持仓」的
`try` 里，而 `cfg` 在该作用域不存在 → `NameError` 被 `except Exception` 吞掉 →
**整个持仓处理块中断**，加密标的全部没被处理。
→ 规则：**给输出补元数据这类「顺手加的一行」，放在函数顶部或 dict 初始化里，
不要塞进他人在维护的 try 块** —— 否则一行小改动能产生与它无关的连锁失效。

## v10.5 变更（2026-09-13 · 补上第四轮漏修的那一条）

### 一、ChatGPT 第四轮 P1「空响应」当时没修

第四轮 ChatGPT 的 P1 共 **4 条**，v10.3 章节头写成 3 条 —— 结果真漏了一条，就是这条：

> HTTP 200 但内容为空时，`response.json() == {}` 不会进入 Exception，
> 会被当成有效数据静默往下传。

可复现：

```
json.loads("{}")        → {}      不抛异常
下游 .get("data", [])   → []      「今天没数据」，而不是「这个源不可用」
```

**报告照出、`severity` 不动、没人知道源挂了** —— 本项目第八次同类形态。

### 二、修的位置和评审建议不一样

评审建议改 `fetch_with_retry`。核实后**不能放那儿**：

| 函数 | 实际调用方 |
|---|---|
| `fetch()` | **1 个**（`get_positions`）|
| `fetch_with_retry()` | **1 个**（一个宏观源）|
| `json.loads(fetch_url(...))` | **16 处** —— 所有数据源都走这条 |

真正的咽喉是 `fetch_url`。守卫加在那里，**16 个抓取点一行都不用改** ——
各调用方原有的 `except` → `record_failure()` 自动生效。

```python
def _read() -> bytes:
    body = urllib.request.urlopen(req, timeout=timeout).read()
    stripped = body.strip()
    if not stripped or stripped in (b"{}", b"[]", b"null"):
        raise ValueError(f"空响应（HTTP 200 但内容为空）: {url[:100]}")
    return body
```

`except ValueError: raise` 前置于代理重试分支 —— 空响应不是网络问题，
再走一次 SOCKS 也是白发。

> **只挡「整个响应体为空」这一层**。体是合法 JSON、只是关键字段空（`{"data": []}`）
> 不在这里判 —— 那属于各源自己的语义，硬判会误伤。边界写进注释，不靠记性。

### 三、契约测试补一条「能真的失败」的检查

新增 `check_empty_response_guard`：5 个假成功（空体 / `{}` / `[]` / `null` / 纯空白）
必须全被拒，外加 1 个**反向**用例 —— `{"data": []}` 必须放行，守卫不得误伤。

拆掉守卫复跑，5 项全红：

```
❌ 契约测试失败（5 项）：
    · [空响应] 200 + 空对象 被当成有效响应 —— 这正是要挡的静默失效
```

契约测试：8 fixture + 29 变异 + **1 项单元检查**（`check_empty_response_guard`）。

### 三、ChatGPT 的 P1：缺失掩码是死参数（本轮挖出的第二个真问题）

v10.2 加了 `missing_out` 出参记录「被填 0 的特征」，**但没有任何调用方传它** —— 死参数。
接线之后发现比预想更严重：

> `compute_macro_features` / `compute_onchain_features` 里每个特征都写在 `if 有值:` 里，
> **源整个挂掉时键被直接省掉** —— 特征向量从 26 个静默缩到 10 个，
> 而掩码只看 `None`/`NaN`，于是**一个都记不到**（正好漏掉最常见的失效形态）。

修法：不可得时**也写键**（值 `None`），由 `build_feature_vector` 统一填 0 并记进掩码。
键集因此恒定在 26 个（与 `ghostfolio_ml.FEATURE_COLS` 对齐），
模型按名字取值、缺的补 0，所以**现网行为不变**。

产物新增 `ml_features_missing`：

```json
{"QQQ": ["exchange_flow", "mvrv", "nupl"], ...}   // ETF 无链上特征
{"binancecoin": ["exchange_flow", "mvrv", "nupl"]} // 源停更（2019-04）
```

`bitcoin` / `ethereum` 不在清单里（链上数据齐全）—— 「缺值填 0」和「真实 0」
终于能在产物里区分开。契约测试另加「**特征形状稳定**」不变量：所有标的的键集必须一致。

### 九、本轮我自己引入的一个回归（值得单独记）

顺着 Grok 第 4 条（「配置里 SGOV 仍是 `signal: "持有"`」）把配置里那个键删掉 ——
Grok 说它「靠 `applicable=false` 映射成固定资产状态，行为正确，只是可读性上重复」。

**删完就错了**：特殊资产的状态**是从配置继承的**（`_sp = dict(_special[sym])`），
键一删，`signals.SGOV.signal` 变成 `None`，于是：

- 报告里 SGOV 的「比昨天」列显示 **`持有→None`**
- 今日状态变化里出现一条**假的告警**：`规则状态从「持有」变为「None」`
- 上游快照被污染（状态存成了 `None`）

**根因不是「删错了键」，而是「状态被存在了配置里」** —— 配置能改空的东西就不是事实。
修法是把状态改成**代码给出**（`_sp["signal"] = "持有"` + `signal_source: code:cash_equivalent`），
配置只留解释性字段（thesis / reasons / risks），并加契约断言：`applicable=false` 的标的
必须有 `signal`（配套变异样本「特殊资产状态被配置改空」）。被污染的那一天快照已修正。

> 教训一句话：**当评审建议你删掉一个「看起来重复」的字段时，先确认它是不是某条链路的唯一来源。**
> 「重复」可能是冗余，也可能是「事实恰好写在配置里」。
